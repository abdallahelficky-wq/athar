# أثر المحاسبي — Backend + Frontend حقيقيان

نظام "أثر المحاسبي": backend حقيقي (هذا المجلد) + واجهة أمامية حقيقية (`frontend/`) مبنيان
وفق [`reference/ATHAR_BACKEND_SPEC.md`](reference/ATHAR_BACKEND_SPEC.md) (مستند التسليم الفني)،
مع استخدام [`reference/AtharAlMuhasabi.jsx`](reference/AtharAlMuhasabi.jsx) (البروتوتايب
الأمامي المرجعي) كحَكَم لكل تفصيلة حسابية أو تصميمية غير واضحة في المستند.

## نطاق هذا التسليم: المرحلة صفر + المراحل 1-3 كاملة

حسب خطة الهجرة في القسم 7 من المستند، هذا التسليم يغطي **المرحلة صفر بالكامل، ثم المراحل
1 و2 و3 بالكامل أيضاً** — أي أن كل موديول تجاري موثّق في المستند له الآن API حقيقي في
هذا الـ backend، ومتصل فعلياً بواجهة `frontend/` (لا توجد موديولات تجريبية متبقية عدا
الزكاة والضريبة، انظر أدناه لماذا).

**المرحلة صفر:**

1. **قاعدة البيانات** — مخطط Prisma كامل (`prisma/schema.prisma`) يغطي كل الجداول الموثّقة
   في القسم 4 من المستند.
2. **نظام المصادقة الحقيقي** — تسجيل/دخول/دعوة/قبول دعوة، JWT (access + refresh مع تدوير
   الرمز)، تشفير كلمات المرور بـ bcrypt، وفصل بيانات كل مستأجر تماماً (multi-tenancy).
3. **API القيود اليومية + شجرة الحسابات + مراكز التكلفة + التقارير المالية الثلاثة**
   (ميزان المراجعة، قائمة الدخل، المركز المالي).

**المرحلة 1 — المبيعات والمشتريات:**

- العملاء والموردون (CRUD كامل).
- عروض الأسعار + تحويلها لفاتورة مبيعات.
- فواتير المبيعات (منشأة/فاتورة ضريبية مبسّطة) مع رمز QR وفق زاتكا (مرحلة التوليد فقط)
  ومنطق شامل/غير شامل الضريبة.
- مردودات المبيعات والمشتريات.
- سندات القبض مع التوزيع على الفواتير وتحديث حالة السداد تلقائياً.
- مبيعات المحطات (لتر × سعر باللتر).
- فواتير المشتريات ومردوداتها.
- تقارير المبيعات والمشتريات.

**المرحلة 2 — المخزون والأصول الثابتة:**

- الأصناف (كود/اسم/وحدة/تكلفة/تصنيف/حد إعادة الطلب).
- حركات المخزون: إدخال، إخراج، صرف مخزني، تحويل بين الفروع (بما فيها التحويل بين شركتين
  مختلفتين عبر حساب "جاري بين الشركات").
- تقرير أرصدة المخزون.
- سجل الأصول الثابتة (بترحيل قيد الشراء تلقائياً)، الإهلاك الشهري بالقسط الثابت،
  الاستبعاد/البيع (مع حساب الربح/الخسارة)، وتقارير الأصول.

**المرحلة 3 — شئون الموظفين:**

- ملفات الموظفين الكاملة (الجنسية، تاريخ الميلاد، البيانات البنكية، المستندات الرسمية
  وتواريخ انتهائها).
- طلبات الإجازات، مستحقات الإجازة الفعلية (حساب/ترحيل/صرف)، مباشرة العودة من الإجازة.
- إجراءات الموظفين (غياب، إضافي، سلفة، مخالفة، عقوبة، إنذار...).
- كشف الرواتب الموسّع بكل أعمدة الإضافات/الخصومات وتوزيعها على شجرة الحسابات حسب القسم 4.8،
  مع الترحيل/فك الترحيل بالرقم السري.
- حساب مكافأة نهاية الخدمة (تقديري توضيحي، بدون قيد محاسبي).
- تقارير الموظفين (تنبيهات انتهاء المستندات).

المراحل القادمة المتبقية من القسم 7 (الموقع التسويقي، الاشتراكات، التكامل الفعلي مع فاتورة)
لم تُبنَ بعد.

## مبدأ التصميم الأساسي

كل معاملة مالية تُنشئ قيداً محاسبياً حقيقياً في `journal_entries` + `journal_entry_lines`،
والتقارير المالية الثلاثة **تُحسب مباشرة من هذه الأسطر** (المرحّلة/posted فقط) ولا تُخزَّن
كأرقام جاهزة في مكان آخر — انظر `src/modules/reports/reports.service.ts`. أي قيد يُرسَل
للحفظ يُرفض من جهة الخادم إن لم يتحقق مجموع المدين = مجموع الدائن (`journalEntries.service.ts`).

## التقنية

Node.js + TypeScript + Express + PostgreSQL + Prisma + JWT + bcrypt + Zod — كما هو مقترح
في القسم 2 من المستند.

## التشغيل محلياً

```bash
cp .env.example .env   # عدّل DATABASE_URL وأسرار JWT حسب بيئتك
npm install
npm run prisma:migrate   # ينشئ قاعدة البيانات ويطبّق المخطط
npm run dev               # يشغّل الخادم على المنفذ 4000 (قابل للتغيير عبر PORT)
```

اختبار سريع:

```bash
curl http://localhost:4000/api/health
```

لزرع بيانات تجريبية (اختياري، بعد تسجيل مستأجر أول عبر `/api/auth/register`):

```bash
npm run prisma:seed
```

### نقاط النهاية الإضافية — المراحل 1-3

`{ pin }` في الجسم) حيثما ينطبق ذلك على مستند مصدر ينشئ قيداً محاسبياً:

```

GET/POST/PATCH/DELETE  /api/sales-returns        + POST /:id/post ، /:id/unpost
GET/POST/PATCH/DELETE  /api/receipts             + POST /:id/post ، /:id/unpost (توزيع على الفواتير)
GET/POST/PATCH/DELETE  /api/station-sales
GET                    /api/sales-reports/...

GET/POST/PATCH/DELETE  /api/suppliers

GET                    /api/purchase-reports/...

GET/POST/PATCH/DELETE  /api/items

GET                    /api/fixed-assets/reports/...
```

كل نقطة نهاية (عدا `/register`, `/login`, `/refresh`, `/logout`, `/accept-invite`) تتطلب
`Authorization: Bearer <accessToken>`، وتُفلتَر تلقائياً بمعرّف المستأجر المستخرج من الرمز —
لا يمكن لأي مستخدم الوصول لبيانات مستأجر آخر (تم اختبار هذا صراحة، انظر أدناه).

### قرارات تصميم توضيحية (لم تُذكر حرفياً في المستند)

- **البريد الإلكتروني للدعوات**: `src/lib/mailer.ts` يحتوي حالياً على "stub" يسجّل رابط
  التفعيل في الطرفية بدل إرساله فعلياً. نقطة الاستبدال بمزوّد حقيقي (Resend/SES/SendGrid)
  محصورة في هذا الملف فقط، حسب اقتراح القسم 2 من المستند.
- **القيود اليدوية تُرحَّل مباشرة عند الإنشاء** (`status: "posted"`) مطابقةً لسلوك
  `JournalModule` في الواجهة المرجعية (زر "ترحيل القيد" ينشئ القيد مباشرة، لا يوجد
  حفظ كمسودة). التعديل/الحذف يتطلبان فك الترحيل أولاً (بخلاف الواجهة الحالية التي تسمح
  بالحذف المباشر بدون رقم سري) — وهذا تطبيق حرفي لما ينص عليه القسم 4.9 صراحة من ضرورة
  حماية أي عملية فك ترحيل برقم سري وتسجيلها في audit log، وهو ما يُنصّ عليه بوضوح كمتطلب
  جديد يجب إضافته للنظام الحقيقي (غير موجود في البروتوتايب).
- **البريد الإلكتروني للمستخدم فريد عالمياً** (`User.email @unique`) وليس مقيّداً بالمستأجر،
  حتى يعمل تسجيل الدخول بمعادلة `{email, password}` فقط دون حاجة لتحديد المستأجر مسبقاً.
- **الرقم السري لفك الترحيل (`unlockPin`)** يُخزَّن مشفّراً بـ bcrypt (وليس نصاً صريحاً كما
  في البروتوتايب) لأنه بوابة أمان حساسة في نظام إنتاج حقيقي.

### قرارات تصميم إضافية — المراحل 1-3 (تفاصيل غير مذكورة حرفياً في المستند)

- **فك ترحيل المستندات المصدرية يحذف القيد المحاسبي بالكامل**، على عكس القيود اليدوية في
  المرحلة صفر (التي تُعاد لحالة draft قابلة للتعديل). فاتورة المبيعات/المشتريات، سند القبض،
  حركة المخزون، تشغيلة الإهلاك، وكشف الرواتب كلها "مستندات مصدر" — فك ترحيلها يحذف
  `JournalEntry` المرتبط تماماً ويعيد المستند لحالة `draft`/غير مرحّل، وإعادة الترحيل تنشئ
  قيداً جديداً بمعرّف مختلف. هذا يطابق طبيعة هذه المستندات في المستند المرجعي (لا يوجد فيها
  مفهوم "تعديل القيد يدوياً" كما في الموديول اليدوي)، ويُبقي `sourceModule`/`sourceId` في
  `JournalEntry` مصدر الحقيقة الوحيد لكل قيد تلقائي.
- **`accountId` مفتاح خارجي حقيقي وليس نص اسم الحساب** في كل بنود الفواتير
  (`SalesInvoiceLine`, `SalesReturnLine`, `PurchaseInvoiceLine`, `PurchaseReturnLine`) —
  البروتوتايب المرجعي يخزّن اسم الحساب كنص حر، لكن في قاعدة بيانات حقيقية هذا يكسر عند
  إعادة تسمية حساب، لذا استُخدمت علاقة `Account` فعلية مع الحفاظ على نفس تجربة الاختيار
  في الواجهة (قائمة منسدلة من شجرة الحسابات الفعلية للشركة).
- **الحسابات "المعروفة" (`getAccountIdByName`)**: كل منطق الترحيل التلقائي (رواتب، إهلاك،
  مستحقات إجازة، تحويل بين الشركات...) يبحث عن الحساب بالاسم المطابق حرفياً لأسماء
  `DEFAULT_CHART_OF_ACCOUNTS` في الواجهة المرجعية. لو حذف المستخدم أحد هذه الحسابات من
  شجرته، يفشل الترحيل بخطأ 400 واضح يذكر اسم الحساب المفقود صراحة، بدل فشل صامت أو
  إنشاء حساب جديد تلقائياً — لأن إنشاء حسابات ضمنياً بصمت يُعتبر أخطر من رفض العملية بوضوح.
- **مبيعات المحطات (`StationSale`) تُبنى على `CostCenter` الموجود** (وليس كياناً جديداً
  مثل "محطة") لأن المستند يصف المحطات كمراكز تكلفة تابعة للشركة، ونموذج `CostCenter` يغطي
  هذا تماماً دون تكرار.
- **التحويل بين الشركات المختلفة**: `StockMovement` من نوع transfer بين شركتين مختلفتين
  يُنشئ **قيدين منفصلين** (واحد بشركة المصدر، وآخر بشركة الوجهة) مرتبطين بنفس
  `transferGroupId`، كل قيد يُوازن عبر حساب "جاري بين الشركات - المجموعة" (مدين في شركة
  المصدر، دائن في شركة الوجهة) — لأن كل `JournalEntry` مربوط بشركة واحدة في المخطط،
  ولا يمكن لقيد واحد أن يوازن بين دفترين مختلفين مباشرة. فك ترحيل أي طرف من التحويل يفك
  الطرفين معاً (يُحدَّدان عبر `transferGroupId`) حفاظاً على تماثل الطرفين دائماً.
- **حساب مكافأة نهاية الخدمة (`GET /employees/:id/eos`) لا يُخزَّن ولا يُنشئ أي قيد
  محاسبي** — هو احتساب تقديري توضيحي فقط وفق المادتين 84 و85 من نظام العمل السعودي،
  ومطابق حرفياً لتحذير الواجهة المرجعية بأنه "يتطلب مراجعة قانونية دقيقة قبل الاعتماد
  الفعلي"، لذا بقي endpoint حسابي بحت (GET) بدون أثر جانبي على قصد.
- **لا يوجد موديول "سند صرف" مستقل للموردين** في هذا التسليم (المستند لا يذكره صراحة في
  قسم المشتريات كما ذكر سندات القبض في المبيعات) — سداد فواتير المشتريات يبقى خارج نطاق
  هذه المرحلة؛ يمكن إضافته لاحقاً بنفس نمط `receipts` إن احتاجه المستخدم.
- **تعديل الأصل الثابت بعد ترحيل قيد الشراء** يُمنع من الخادم لحقول التكلفة/تاريخ الشراء
  (تُقفل بعد إنشاء القيد)، بينما تبقى حقول وصفية مثل الاسم قابلة للتعديل — لأن تغيير التكلفة
  بعد الترحيل يكسر تطابق دفتر الأصول مع القيد المحاسبي الفعلي دون آلية تسوية.
- **إجراءات الموظفين الدفعية (`hr-actions` batch)**: `POST` يقبل `employeeIds[]` لإنشاء
  نفس الإجراء (غياب/إضافي/سلفة...) لعدة موظفين في طلب واحد، مطابقاً لواجهة "مجموعة محددة/
  كل الموظفين" في البروتوتايب المرجعي، بدل إجبار الواجهة الأمامية على استدعاء الـ API
  عدة مرات في حلقة.

## ما تم اختباره يدوياً (smoke test)

- تسجيل مستأجر جديد (زرع شجرة الحسابات تلقائياً — 36 حساباً مطابقة تماماً لثابت `ACCOUNTS`
  في الواجهة المرجعية).
- إنشاء شركة ومركز تكلفة وقيد يومية متوازن، وظهوره فوراً في التقارير الثلاثة بأرقام متطابقة
  مع منطق `aggregateAccounts`/`TrialBalanceReport`/`IncomeStatementReport`/`BalanceSheetReport`
  في الواجهة المرجعية.
- رفض قيد غير متوازن من جهة الخادم (400).
- فك ترحيل بكلمة سر خاطئة (403) وبكلمة سر صحيحة (200) + تسجيل الحدث في `audit_logs`.
- استبعاد القيود غير المرحّلة (draft) من التقارير المالية بعد فك الترحيل.
- عزل بيانات المستأجرين: مستأجر ثانٍ لا يرى شركات المستأجر الأول، ومحاولة تعديلها تُرفض (404).
- تدوير refresh token: إعادة استخدام رمز تحديث سابق بعد استخدامه تُرفض (401).

## الأرشفة الإلكترونية للمستندات + إنشاء قيود بالذكاء الاصطناعي

إضافتان جديدتان تُبنيان فوق كل ما سبق:

### 1) الأرشفة الإلكترونية (مرفقات)

موديول عام (`Attachment`) قابل لإعادة الاستخدام عبر أي معاملة: قيد يومية، فاتورة مبيعات،
مردود مبيعات، سند قبض، فاتورة مشتريات، مردود مشتريات، كشف رواتب، تسوية إجازة، أصل ثابت.
التخزين الفعلي على Cloudflare R2 (متوافقة مع S3 API) عبر `@aws-sdk/client-s3`.

```
POST   /api/attachments      رفع ملف (multipart: file, entityType, entityId) — حتى 15MB
GET    /api/attachments      ?entityType=&entityId= — قائمة مرفقات معاملة معيّنة
DELETE /api/attachments/:id  حذف من قاعدة البيانات ومن الحاوية معاً
```

في الواجهة: `frontend/src/wired/shared/AttachmentsPanel.jsx` — مكوّن واحد يُستدعى بـ
`<AttachmentsPanel entityType="..." entityId={id} />` من داخل الشاشات التسعة أعلاه (زر
"المرفقات" يفتح/يطوي لوحة المرفقات أسفل كل سطر/سجل).

**قرارات تصميمية**:
- **`entityType` نص حر (String) وليس enum على مستوى قاعدة البيانات** — يُتحقَّق منه فقط في
  طبقة الـ API (zod enum بالأنواع التسعة المطلوبة صراحة)، على غرار `sourceModule`/`sourceId`
  في `JournalEntry`. هذا يجعل الموديول قابلاً للتوسّع لأي كيان مستقبلي دون أي migration جديد.
- **لا تحقّق FK صارم من أن `entityId` ينتمي فعلاً لسجل موجود** — تماماً كنمط `sourceId`
  الموجود مسبقاً في `JournalEntry`. الأمان محفوظ رغم ذلك لأن كل استعلام مُفلتَر بـ
  `tenantId` أولاً؛ أسوأ سيناريو هو أن يُرفق مستخدم ملفاً بمعرّف وهمي **ضمن مستأجره هو نفسه**،
  وهذا لا يسرّب شيئاً لمستأجر آخر (تم اختباره صراحة، انظر أدناه).
- **لا يُخزَّن رابط دائم (`fileUrl`) في قاعدة البيانات** — يُخزَّن فقط `fileKey` (مسار الملف
  الدائم داخل الحاوية)، بينما `fileUrl` المُعاد في كل استجابة API هو رابط مؤقت (presigned
  URL صالح لساعة واحدة) يُولَّد عند كل طلب عبر `getSignedUrl`. هذا يعمل بغض النظر عن كون
  حاوية R2 عامة (public) أو خاصة، ولا يُسرِّب رابطاً دائماً لو أُلغيت صلاحية الوصول لاحقاً.
- **`forcePathStyle: true`** في عميل S3 — مدعوم رسمياً من R2، وضروري لأي بديل S3 اختباري
  محلي (كما استُخدم في الاختبار أدناه)، دون أي تأثير سلبي على R2 الحقيقية.

### 2) إنشاء قيود تلقائياً من المستندات بالذكاء الاصطناعي

`POST /api/journal-entries/from-document` (multipart: `file`, `companyId`) — يقرأ Claude
(عبر Anthropic Messages API بقدرة الرؤية، `ANTHROPIC_API_KEY` + `ANTHROPIC_MODEL`) صورة أو
PDF لمستند مالي، ويقترح تاريخاً ووصفاً وطرفاً ومبلغاً وضريبة، ثم يختار **حساباً مديناً
وحساباً دائناً من شجرة حسابات هذا المستأجر الفعلية فقط** (تُرسَل كاملة ضمن الـ prompt)،
فيُنشئ قيداً بحالة **draft** (`sourceModule: ai_document`) ويربط المستند المرفوع به تلقائياً
عبر جدول `Attachment` — لا يُرحَّل تلقائياً أبداً، ويمر بنفس تحقق توازن المدين/الدائن
المستخدَم لأي قيد يدوي (`assertBalanced` نفسها).

في الواجهة: زر "إنشاء قيد من مستند (ذكاء اصطناعي)" في شاشة القيود اليومية يفتح
`CreateFromDocumentModal.jsx` — رفع الملف، ثم عرض القيد المقترح **قابلاً للتعديل الكامل**
بجانب صورة المستند نفسها للمقارنة، بزرّين منفصلين: "حفظ كمسودة" (PATCH على القيد المُنشَأ
مسبقاً كـ draft) و"موافقة وترحيل" (نفس PATCH ثم `POST /:id/post` الحالي صراحة).

**قرارات تصميمية**:
- **الرد بصيغة JSON عبر تقنية الـ prefill** (رسالة "assistant" تبدأ بـ `{`) بدل الاعتماد على
  توجيه نصي فقط في الـ prompt — تقنية موثّقة وموثوقة لإجبار Claude على إخراج JSON خالص دون
  أي شرح إضافي حوله، أكثر قوة من مجرد طلب "أجب بصيغة JSON" في النص.
- **النموذج يُطلَب منه إرجاع `id` الحساب بالضبط** (وليس اسمه فقط) من القائمة المُرسَلة إليه،
  ويُتحقَّق خادمياً أن كلا المعرّفين موجودان فعلاً في شجرة حسابات المستأجر وأنهما مختلفان عن
  بعضهما — أي اقتراح غير صالح يُرفَض بخطأ عربي واضح **قبل** إنشاء أي قيد، بدل إنشاء قيد بحساب
  وهمي أو حسابين متطابقين (غير منطقي محاسبياً).
- **`amount` هو المبلغ الإجمالي شامل الضريبة** ويُستخدَم كما هو في طرفي القيد (سطرين فقط:
  مدين/دائن بنفس المبلغ)؛ `vat_amount` معلومة سياقية تُضاف كملاحظة نصية داخل بيان القيد
  (`memo`) بدل تقسيم القيد إلى ثلاثة أسطر — المستند لم يحدد بنية محاسبية معيّنة لتوزيع
  الضريبة على حساب "ضريبة القيمة المضافة - مدخلات" تلقائياً، وهذا قرار يستحق مراجعة محاسبية
  بشرية بدل افتراضه آلياً.
- **لا ترحيل تلقائي مهما كانت ثقة النموذج** — القيد يُنشأ دائماً كـ `draft` فقط، والترحيل
  يتطلب زراً صريحاً من المستخدم بعد المراجعة، تماماً كما طُلب صراحة.
- **`ANTHROPIC_MODEL` و`ANTHROPIC_BASE_URL` متغيّرا بيئة اختياريان** (بقيمتين افتراضيتين:
  `claude-sonnet-4-6` وعنوان Anthropic الحقيقي) بدل تثبيت القيمتين في الكود مباشرة — يسمح
  بتغيير النموذج مستقبلاً أو توجيه الطلبات عبر وسيط (proxy) دون تعديل الشيفرة.

### كيف اختُبرت الميزتان فعلياً (وليس افتراضاً)

بيئة هذه الجلسة لا تملك بيانات اعتماد R2 أو ANTHROPIC_API_KEY حقيقية (هذه أسرار إنتاج على
Railway فقط)، فتم التحقق من **مسار الشيفرة الفعلي بالكامل** (نفس أكواد `@aws-sdk/client-s3`
واستدعاء `fetch` الحقيقي لصيغة Anthropic Messages API) ضد بديلين حقيقيين متوافقين تماماً مع
نفس الواجهات، بدل تخطي الاختبار أو الاكتفاء بمراجعة الكود:

- **للمرفقات**: خادم `s3rver` (تطبيق Node.js حقيقي لبروتوكول S3) شغّال محلياً، مع
  `forcePathStyle: true` — تم فعلياً: رفع ملف عبر `POST /api/attachments`، توليد رابط
  presigned حقيقي وتنزيله والتأكد أن محتواه مطابق بايتاً لبايت للملف الأصلي (نص عربي)،
  عرض القائمة، حذف المرفق والتأكد من زوال الملف من الحاوية نفسها (404 عند إعادة طلبه)،
  وأخيراً عزل بين مستأجرين: مستأجر آخر لا يرى مرفقات مستأجر أول ولا يستطيع حذفها (404).
- **للذكاء الاصطناعي**: خادم وهمي محلي بنفس شكل استجابة Anthropic Messages API بالضبط
  (بما فيها تقنية الـ prefill)، **يقرأ شجرة الحسابات الحقيقية فعلياً من الـ prompt المُرسَل
  من الخادم** (لا بيانات وهمية ثابتة) ليحاكي اختيار Claude لحساب موجود بالفعل. تم فعلياً عبر
  المتصفح (Playwright): رفع صورة، تحليلها، إنشاء قيد draft بحساب مدين "تكلفة البضاعة المباعة"
  وحساب دائن "البنك الأهلي - حساب تشغيلي" (كلاهما من الـ 36 حساباً الحقيقية لهذا المستأجر)،
  بيان يتضمّن الوصف والطرف ومبلغ الضريبة، مرفق مرتبط تلقائياً، ثم "موافقة وترحيل" ونجاح
  الترحيل الفعلي (يظهر "مرحّل" في قائمة القيود). كذلك اختُبرت مسارات الرفض الدفاعية: نوع ملف
  غير مدعوم، معرّف حساب غير موجود، نفس الحساب مديناً ودائناً، مبلغ صفري، ورد غير منظّم
  (non-JSON) من النموذج — كل حالة تُرفض بخطأ عربي واضح دون إنشاء أي قيد يتيم.
- **اختبار متصفح حقيقي (Playwright) لكامل الرحلتين معاً**: تسجيل حساب، إنشاء قيد يدوي، فتح
  لوحة "المرفقات" ورفع مستند وظهوره فوراً في الجدول، ثم "إنشاء قيد من مستند" وموافقة وترحيل
  — صفر أخطاء JavaScript في المتصفح طوال الرحلة.

**محدودية معروفة يجب الإفصاح عنها**: جودة قراءة Claude الفعلية لمستندات حقيقية (دقّة استخراج
المبلغ/التاريخ/اختيار الحساب من صورة فاتورة حقيقية) لم تُختبَر في هذه الجلسة لعدم توفّر مفتاح
Anthropic حقيقي هنا — الذي اختُبر فعلياً هو مسار الشيفرة الكامل (الطلب، شجرة الحسابات
المُضمَّنة، تحليل الرد، إنشاء القيد، الربط بالمرفق، الرفض الدفاعي) وهو المسؤول عن صحة النظام
بغض النظر عن جودة أي استجابة معيّنة. يُنصَح باختبار عيّنة من مستندات حقيقية بعد النشر على
Railway (حيث المفتاح الحقيقي متاح) للتأكد من جودة الاقتراحات على حالات واقعية.

## حادثة إنتاج: migrations لم تُطبَّق تلقائياً على Railway (وإصلاحها الدائم)

بعد نشر ميزتي الأرشفة والذكاء الاصطناعي، ظهر هذا الخطأ في سجلات Railway عند محاولة حفظ
وترحيل فاتورة مبيعات:

```
PrismaClientKnownRequestError, code: 'P2022'
at async createHandler (/app/dist/modules/salesInvoices/salesInvoices.controller.js:52:26)
```

**السبب الجذري المؤكَّد** (وليس افتراضاً): تم استنساخ الخطأ محلياً بدقة — قاعدة بيانات
بها فقط أول migration (`20260721193512_phase_zero_init`، التي أنشأت `sales_invoice_lines`
بعمود `account TEXT` قديم) دون أي من الـ 4 migrations اللاحقة، ثم تشغيل الخادم المبني
(`node dist/server.js`) وإرسال نفس طلب حفظ فاتورة مبيعات — أنتج **نفس الخطأ بالضبط**، حتى
رقم السطر (`salesInvoices.controller.js:52:26`):

```
PrismaClientKnownRequestError: The column `accountId` does not exist in the current database.
    code: 'P2022', meta: { modelName: 'SalesInvoice', column: 'accountId' }
```

أي أن قاعدة بيانات الإنتاج على Neon لم تكن متأخرة بـ migration الأرشفة الجديد فقط كما بدا
في البداية، بل **لم يُشغَّل عليها `prisma migrate deploy` منذ نشر مراحل 1-3 نفسها** (العمود
`accountId` أُضيف حينها، وليس في هذا التسليم) — أي أن كل الـ 4 migrations اللاحقة لـ Phase Zero
كانت معلَّقة، وليس migration واحد فقط.

**لماذا حدث هذا رغم نجاح النشر**: لأن سكربت `start` كان `"node dist/server.js"` فقط — لا شيء
في عملية البناء أو التشغيل على Railway يطبّق migrations تلقائياً؛ كان تطبيقها يعتمد كلياً على
تذكّر تشغيل `npx prisma migrate deploy` يدوياً بعد كل نشر يتضمّن تعديلاً في المخطط.

**الإصلاح الدائم** (`package.json`):

```diff
- "start": "node dist/server.js",
+ "start": "prisma migrate deploy && node dist/server.js",
```

بهذا يُطبَّق أي migration معلَّق **تلقائياً في كل مرة يُقلَع فيها الخادم** (كل نشر جديد على
Railway يُعيد تشغيل `npm start`)، قبل أن يبدأ الخادم استقبال أي طلب — لا حاجة لتذكّر خطوة
يدوية بعد اليوم مع أي جدول أو migration مستقبلي. كذلك نُقلت حزمة `prisma` (الـ CLI) من
`devDependencies` إلى `dependencies` في `package.json`، لأن بعض منصّات النشر (ومنها احتمالياً
Railway حسب إعداد Nixpacks) قد تُقلّص `devDependencies` بين مرحلة البناء والتشغيل، ما كان
سيجعل أمر `prisma migrate deploy` نفسه غير موجود وقت الإقلاع الفعلي رغم نجاحه أثناء البناء.

**التحقق الكامل من الإصلاح** (وليس افتراضاً): بعد تطبيق التعديل أعلاه، أُعيد تشغيل نفس قاعدة
البيانات المتأخرة (4 migrations معلَّقة) عبر `npm run build && npm start` (بالضبط كما يفعل
Railway) — ظهر في السجل تطبيق الأربعة migrations تلقائياً بنجاح:

```
Applying migration `20260722101827_phases_1_3_sales_purchases_inventory_assets_hr`
Applying migration `20260722102927_stock_movement_transfer_group`
Applying migration `20260722103500_depreciation_run_unique_month`
Applying migration `20260726123822_attachments_and_ai_source_module`
All migrations have been successfully applied.
```

ثم أُعيدت نفس عملية حفظ وترحيل فاتورة المبيعات التي فشلت سابقاً — نجحت هذه المرة بالكامل
(فاتورة برقم `INV-00001`، حالة `posted`، رمز QR مُولَّد، قيد محاسبي مرتبط)، و`npx prisma
migrate status` أكّد أن قاعدة البيانات "up to date" تماماً بعد ذلك.

**ملاحظة مهمة لتفعيل الإصلاح فعلياً على Railway**: هذا التعديل يعمل تلقائياً فقط إذا كان
Railway يستخدم فعلياً سكربت `start` من `package.json` (السلوك الافتراضي لـ Nixpacks مع
مشروع Node قياسي). إن كان هناك Start Command مخصَّص مضبوط يدوياً في إعدادات Railway
(Settings → Deploy → Custom Start Command) فسيتجاوز هذا التعديل تماماً — تأكّد من عدم وجود
أمر مخصَّص هناك، أو حدِّثه ليطابق `prisma migrate deploy && node dist/server.js` إن وُجد، حتى
يعمل الإصلاح فعلياً على النشرة القادمة. لم يكن بإمكاني تعديل إعدادات Railway نفسها من هذه
الجلسة (لا صلاحية وصول لوحة تحكم Railway أو بيانات اعتماد قاعدة الإنتاج)؛ التعديل هنا محصور
بملفات المستودع فقط.

# الواجهة الأمامية الحقيقية (`frontend/`)

مشروع React حقيقي (Vite، متعدد الملفات — **ليس** ملفاً واحداً) يستبدل طبقة الـ state المحلي
في البروتوتايب المرجعي بطبقة API حقيقية خلفها. بعد هذا التسليم، **كل الموديولات التجارية
متصلة فعلياً بالـ backend الحقيقي**: تسجيل الدخول/التسجيل، لوحة القيادة، القيود اليومية،
شجرة الحسابات، التقارير المالية الثلاثة، المبيعات، المشتريات، المخزون، الأصول الثابتة،
وشئون الموظفين بالكامل. الموديول التجريبي الوحيد المتبقي عمداً هو **الزكاة والضريبة**
(تقديري توضيحي في المستند نفسه، بلا نموذج بيانات موثّق ولا نقطة API مطلوبة)، وتبويب
"المستخدمون" في الإعدادات (إدارة المستخدمين/الدعوات تُدار فعلياً من `/api/auth/invite`
لكن شاشة الإعدادات التفصيلية لها بقيت بالنمط التجريبي لأنها لم تكن ضمن نطاق هذا الطلب).

## التشغيل محلياً (خطوة بخطوة)

يحتاج المشروع تشغيل **الـ backend أولاً**، ثم الواجهة الأمامية في نافذة طرفية أخرى.

```bash
# 1) شغّل قاعدة البيانات (إن لم تكن تستخدم Neon أو قاعدة سحابية جاهزة بالفعل)
#    وطبّق المخطط، من مجلد الـ backend (جذر المستودع):
cp .env.example .env            # عدّل DATABASE_URL ليشير لقاعدتك (Neon أو محلية)
npm install
npm run prisma:migrate
npm run dev                     # الـ backend يعمل الآن على http://localhost:4000

# 2) في نافذة طرفية أخرى، شغّل الواجهة الأمامية:
cd frontend
cp .env.example .env            # VITE_API_URL=http://localhost:4000/api (عدّله لو الـ backend على منفذ/دومين مختلف)
npm install
npm run dev                     # الواجهة تعمل الآن على http://localhost:5173
```

افتح `http://localhost:5173` في المتصفح، اضغط "ابدأ تجربتك المجانية"، سجّل حساباً جديداً
(يُنشئ مستأجراً حقيقياً + شجرة حسابات افتراضية في قاعدة البيانات فعلياً)، ثم من لوحة
القيادة أنشئ أول شركة (كل مستأجر جديد يبدأ بدون شركات)، وابدأ تسجيل قيود يومية حقيقية
من تبويب **الحسابات ← القيود اليومية**، وشاهدها تنعكس فوراً في **التقارير**.

للبناء الإنتاجي: `npm run build` داخل `frontend/` (يُخرج ملفات ثابتة في `frontend/dist/`
تُقدَّم عبر أي استضافة ثابتة، بشرط ضبط `VITE_API_URL` وقت البناء لعنوان الـ backend الفعلي).

## ما الذي يتصل فعلياً بالـ API الحقيقي، وما الذي بقي تجريبياً محلياً

| الجزء | الحالة |
|---|---|
| تسجيل حساب / تسجيل دخول / تجديد الجلسة تلقائياً | **حقيقي** — `/api/auth/*`، الرمزان مخزَّنان في `localStorage` ومرفقان تلقائياً بكل طلب |
| لوحة القيادة | **حقيقي** — عدد القيود، حجم الحركة المرحّلة، صافي الربح، آخر القيود |
| القيود اليومية (عرض/إنشاء/تعديل/حذف/ترحيل/فك ترحيل بالرقم السري/استيراد) | **حقيقي بالكامل** — بما فيها التحقق من توازن القيد من جهة الخادم |
| شجرة الحسابات | **حقيقي** — إضافة/تعديل/حذف حساب فعلي في قاعدة البيانات |
| التقارير الثلاثة (ميزان المراجعة، قائمة الدخل، المركز المالي) | **حقيقي** — محسوبة من القيود المرحّلة الفعلية |
| بيانات الشركات (الإعدادات) | **حقيقي** — تعديل/حذف الشركات الفعلية |
| المبيعات (عملاء، عروض أسعار، فواتير + QR زاتكا، مردودات، سندات قبض، مبيعات محطات، تقارير) | **حقيقي بالكامل** |
| المشتريات (موردون، فواتير، مردودات، تقارير) | **حقيقي بالكامل** |
| المخزون (أصناف، حركات إدخال/إخراج/صرف/تحويل بين الفروع وبين الشركات، تقرير أرصدة) | **حقيقي بالكامل** |
| الأصول الثابتة (سجل، إهلاك شهري، استبعاد/بيع، تقارير) | **حقيقي بالكامل** |
| شئون الموظفين (ملفات، إجازات، مستحقات إجازة، مباشرة عودة، إجراءات، رواتب، نهاية خدمة، تقارير) | **حقيقي بالكامل** |
| الزكاة والضريبة | **تجريبي محلي كما كان** — تقديري توضيحي في المستند نفسه، بلا نموذج بيانات موثّق |
| مستخدمو الإعدادات (شاشة الإدارة التفصيلية) | **تجريبي محلي كما كان** — خارج نطاق هذا التسليم |

**ملاحظة تصميمية:** كل الموديولات الحقيقية أعلاه (بما فيها المبيعات/المشتريات/المخزون/
الأصول/الموظفين الجديدة) تستخدم الآن **نفس منتقي "الشركة (بيانات حقيقية)"** المستخدَم في
لوحة القيادة والقيود والتقارير — لا يوجد أكثر من مفهوم "شركة" في الواجهة بعد هذا التسليم.
الموديول التجريبي المتبقي (الزكاة) وحده ما زال يستخدم الشركات الثابتة المحلية القديمة
(تيسم/أوراد/ارمي/QAS) لأنه لم يُبنَ له API بعد.

### إصلاح ترميز النصوص العربية ("????")

هذه المشكلة مرّت بثلاث جولات تشخيص، وكل جولة كشفت طبقة مختلفة تماماً عن السابقة:

**الجولة 1 — عنوان `<title>` فقط**: خادم Vite للتطوير كان يرسل `index.html` بترويسة
`Content-Type: text/html` بدون `charset=utf-8` صريح، فيعتمد المتصفح على `<meta charset>`
داخل الملف، لكن حقنة Vite لكود HMR قبل وسم meta كانت تُحدث سباقاً يجعل المتصفح يخمّن ترميزاً
خاطئاً أحياناً. الحل حينها: فرض `charset=utf-8` على ترويسة استجابة `index.html`.

**الجولة 2 — نصوص أخرى في الصفحة استمرت تظهر "????" رغم إصلاح العنوان**: تبيّن أن كل ملفات
JS/CSS المخدَّمة من خادم التطوير (`.jsx`/`.js`/`.css` — وهي حيث تعيش كل النصوص العربية التي
يحقنها React، بخلاف `<title>` الثابت في `index.html`) كانت تُرسَل بترويسة `Content-Type:
text/javascript`/`text/css` **بدون أي `charset` على الإطلاق** (تأكد ذلك بفحص مباشر
`curl -I`). الحل: تعميم middleware واحد (`forceUtf8Text()` في `frontend/vite.config.js`)
يفرض `charset=utf-8` على أي استجابة HTML/JS/CSS/JSON تفتقر له، في وضعي التطوير والمعاينة معاً.

**الجولة 3 — نفس العرَض ("????") استمر تحديداً في عنصرين فقط (السطر العلوي `.topbar-company`
والعنوان الفرعي بالشريط الجانبي `.brand-sub`) رغم أن كل النصوص الثابتة المجاورة لهما مباشرة
في نفس الملفات (مثل "أثر المحاسبي" و"نظرة عامة — بيانات حقيقية") كانت تظهر سليمة تماماً**:
هذا التناقض تحديداً هو ما كشف السبب الحقيقي. فحص الكود المصدري لهذين العنصرين
(`frontend/src/App.jsx`) أظهر أنهما **لا يحتويان أي نص حرفي (string literal) على الإطلاق**
— كلاهما تعبير ديناميكي بحت: `{tenant?.name}` و`{user?.name} — {tenant?.name}`. بما أن مشكلة
ترميز على مستوى الملف/الترويسة كانت ستُفسِد كل نص في نفس الاستجابة بلا تمييز (وليس عنصرين
ديناميكيين محددين بينما النصوص الثابتة المجاورة سليمة)، فهذا يستبعد تماماً أي علاقة بمشكلة
transport/charset، ويثبت أن العطب في **القيمة المخزَّنة فعلياً** لاسم المستأجر (tenant.name)
وربما اسم المستخدم — أي بيانات قديمة تالفة في قاعدة البيانات نفسها (مثلاً من إدخال يدوي مبكر
بترميز غير UTF-8 قبل بدء التحقق من الترميز في هذا الإصلاح)، **وليس خللاً في كود العرض**.

تم التحقق من هذا التشخيص بشكل قاطع (وليس افتراضياً) عبر تجربة استنساخ كاملة: تسجيل مستأجر
جديد باسم عربي صحيح (ظهر بشكل سليم تماماً)، ثم **تعمّد إفساد** قيمة `tenants.name` مباشرة في
قاعدة البيانات لتصبح حرفياً سلسلة من علامات `?` (محاكاة تماماً للعرَض المُبلَّغ عنه)، ثم
تسجيل خروج ودخول من جديد (طلب شبكة فعلي جديد بالكامل، لا كاش) — والنتيجة: نفس علامات `?`
الحرفية تظهر بعد هذه الدورة الكاملة، مثبتةً أن الأنبوب (pipeline) يعرض بأمانة أي قيمة
مخزَّنة فعلياً، صحيحة كانت أو تالفة.

**المشكلة الحقيقية المكتشفة بهذا الفحص**: لم يكن هناك أي مسار في التطبيق لتصحيح اسم المنشأة
(tenant) بعد التسجيل الأول — لا `endpoint`، ولا شاشة إعدادات. فإن حدث خطأ في القيمة المخزَّنة
لأي سبب، لم تكن هناك طريقة لإصلاحه سوى التعديل المباشر في قاعدة البيانات.

**الحل**: أُضيف مسار كامل لتصحيح اسم المنشأة:
- `PATCH /api/auth/tenant` (`admin`/`finance_manager` فقط) — `src/modules/auth/auth.service.ts`
  دالة `updateTenantName`.
- شاشة **الإعدادات ← بيانات الشركات** تعرض الآن لوحة "اسم المنشأة" في الأعلى (قبل جدول
  الشركات) بزر "تعديل الاسم" — `frontend/src/wired/CompaniesSettings.jsx` (مكوّن
  `TenantNameSettings`)، وتحدَّث الجلسة محلياً فوراً بعد الحفظ عبر `renameTenant()` الجديدة في
  `AuthContext`.

أُعيد تشغيل تجربة الاستنساخ الكاملة بعد هذا الإصلاح: بعد إفساد `tenants.name` عمداً وتأكيد
ظهور "????" حتى بعد تسجيل دخول جديد بالكامل، استُخدمت شاشة الإعدادات الجديدة لإعادة كتابة
الاسم — وتأكّد فوراً (عبر `innerText` الفعلي لكل من `.topbar-company` و`.brand-sub`، وليس
فحصاً بصرياً فقط) أن كلا العنصرين يعرضان النص العربي الصحيح بلا أي حرف `?` بعد الحفظ مباشرة.

**الجولة 4 — بعد تصحيح اسم المستأجر، استمر ظهور "????" في نفس العنصرين تحديداً**: بما أن
`.topbar-company` يعرض `{user?.name} — {tenant?.name}` وليس اسم المستأجر فقط، فإن الجزء
المتبقي المحتمل هو `user.name` نفسه (اسم المستخدم صاحب الجلسة) — وهو حقل لم يكن له أي مسار
تصحيح على الإطلاق (لا `endpoint`، ولا شاشة)، تماماً كحال `tenant.name` قبل الجولة 3. الأخطر:
لم يكن هناك أصلاً أي آلية لتحديث `user`/`tenant` المخزَّنين في `localStorage` بعد أول تسجيل
دخول — فحتى بعد تصحيح البيانات في قاعدة البيانات (بأي وسيلة)، تبقى أي جلسة متصفح مفتوحة من
قبل ذلك تعرض القيمة القديمة **إلى الأبد** ما لم يُسجَّل الخروج والدخول يدوياً من جديد، لأن
التطبيق كان يعتمد كلياً على البيانات المخزَّنة محلياً وقت الدخول دون أي إعادة تحقّق لاحقة.

**الحل**:
- `GET /api/auth/me` (أي مستخدم مسجّل دخوله) — يُعيد أحدث نسخة من `user`/`tenant` من قاعدة
  البيانات مباشرة، ويُستدعى تلقائياً عند فتح التطبيق (`AuthContext`) لتحديث الجلسة المخزَّنة
  محلياً بأحدث قيمة حقيقية، بدل الاكتفاء بما كان محفوظاً وقت آخر تسجيل دخول — هذا يُصلح
  تلقائياً أي جلسة قديمة متأثرة بمجرد إعادة تحميل الصفحة، دون الحاجة لتسجيل خروج/دخول يدوي.
- `PATCH /api/auth/me` (أي مستخدم مسجّل دخوله) — لتصحيح اسمه الشخصي.
- لوحة "اسمي" الجديدة في **الإعدادات ← الملف الشخصي** (أعلى الشاشة التجريبية القديمة)
  — `frontend/src/wired/MyAccountSettings.jsx` — تستخدم `renameMe()` الجديدة في `AuthContext`.

تم التحقق مجدداً بنفس منهجية الاستنساخ الكاملة، هذه المرة لكلا الحقلين معاً: تسجيل حساب جديد
باسمين عربيين صحيحين (مستخدم ومستأجر)، ثم إفساد `users.name` و`tenants.name` معاً مباشرة في
قاعدة البيانات، ثم مجرّد إعادة تحميل الصفحة (بدون تسجيل خروج) — وتأكّد ظهور الإصلاح التلقائي
عبر `/auth/me` للقيمتين التالفتين معاً في كلا العنصرين. بعدها استُخدمت لوحتا "بيانات الشركات"
و"الملف الشخصي" لتصحيح الاسمين من داخل نفس الجلسة، وتأكّد فوراً (عبر `innerText` الفعلي) أن
`.topbar-company` و`.brand-sub` يعرضان النص الصحيح بلا أي حرف `?`. ثم أُعيد تسجيل الخروج
والدخول من جديد للتأكد من ثبات الإصلاح عبر جلسة جديدة بالكامل — نفس النتيجة الصحيحة.

## ما تم اختباره يدوياً (متصفح حقيقي عبر Playwright، وليس فقط build ناجح)

**المرحلة صفر (سابقاً):**

- تسجيل حساب جديد فعلياً → وصول للوحة القيادة الحقيقية.
- إنشاء أول شركة (تجربة "مستأجر بلا شركات" التي يبدأ بها أي حساب جديد).
- تسجيل قيد يومية حقيقي متوازن (نقدية 1,000 مدين / مبيعات 1,000 دائن) وترحيله.
- ظهور نفس الرقمين بالضبط في ميزان المراجعة (متوازن ✓) وقائمة الدخل والمركز المالي.
- إعادة تحميل الصفحة (`F5`) والتأكد من بقاء الجلسة مسجَّلة دخول وعرض نفس البيانات الحقيقية.

**المراحل 1-3 (هذا التسليم):**

على مستوى الـ backend، اختبار Python شامل (`smoke_test.py`) يغطي كل موديول عبر استدعاءات
HTTP حقيقية على قاعدة بيانات فعلية: إنشاء عميل/مورد/صنف/موظف، فاتورة مبيعات مع QR زاتكا
ومنطق شامل/غير شامل الضريبة، تحويل عرض سعر لفاتورة، سند قبض بتوزيع تلقائي على الفواتير
وتحديث حالة السداد، فاتورة مشتريات، حركة مخزون تحويل بين فرعين وبين شركتين مختلفتين (تحقّق
من توازن كل من القيدين الناتجين على حدة)، تسجيل أصل ثابت وترحيل قيد شرائه، تشغيلة إهلاك
شهري وترحيلها وفك ترحيلها بالرقم السري، استبعاد أصل مع حساب الربح/الخسارة، طلب إجازة،
معاينة/إنشاء/صرف مستحقات إجازة (والتحقّق من توازن القيدين الناتجين)، إجراء موظف دفعي،
كشف رواتب (إنشاء/تعديل صف/ترحيل/فك ترحيل بالرقم الخاطئ ثم الصحيح)، وأخيراً تحقّق شامل من
سلامة ميزان المراجعة الكلي (كل الحسابات لا تزال متوازنة بعد كل هذه العمليات مجتمعة) وعزل
بيانات المستأجرين. **كل الفحوصات نجحت.**

على مستوى الواجهة الأمامية، بعد ربط الموديولات الخمسة الجديدة فعلياً في `App.jsx` (بدل
الشاشات القديمة)، تحقّقت من:

- نجاح `npx vite build` بدون أخطاء (عدد الوحدات المجمَّعة قفز من 136 إلى 190 وحدة، ما يؤكد
  أن كل الملفات الجديدة أصبحت فعلياً قابلة للوصول من نقطة الدخول ولم تعد "ملفات يتيمة").

- التنقل عبر كل تبويبات المبيعات/المشتريات/المخزون/الأصول الثابتة/شئون الموظفين (بما فيها
  الثمانية تبويبات الفرعية لشئون الموظفين: الملفات، الإجازات، المستحقات، المباشرة بعد
  الإجازة، الإجراءات، الرواتب، نهاية الخدمة، والتقارير) والتأكد من عرضها الصحيح بدون أي

  الرصيد المتراكم) فور اختيار الموظف وتاريخ بداية الإجازة.
- التأكد من ظهور عناوين الصفحات والتنقّل والنماذج بالعربية الصحيحة في كل شاشة (لا توجد
  أي "????" — تأكيد إضافي لإصلاح UTF-8 أعلاه) عبر `document.title` وفحص بصري لكل لقطة شاشة.

## إعادة تصميم شاشة فواتير المبيعات (فصل الإنشاء عن القائمة + صف إجراءات كامل)

الشاشة القديمة كانت فورم إنشاء + جدول قائمة في نفس الصفحة. أُعيد تصميمها بالكامل بناءً على
طلب توضيحي مفصّل، مع فصل واضح بين "الإنشاء" (نافذة Modal) و"القائمة" (شاشة عرض وإجراءات).

### القرارات التصميمية (بعد توضيح صريح من المستخدم عبر أسئلة تفصيلية)

- **كتالوج "أصناف قابلة للبيع" منفصل تماماً عن جدول `Item` (المخزون):** جدول `Item` الحالي
  لا يحتوي سعر وحدة افتراضي أو حساب إيراد مرتبط أو علم خضوع للضريبة — وهي بيانات لا معنى
  لها لصنف مخزني (الذي يُدار بالكمية/التكلفة لا بسعر بيع). بدل تحميل `Item` بحقول لا تخصه،
  أُضيف موديل `SellableItem` جديد (`name`, `defaultUnitPrice`, `vatApplicable`,
  `defaultRevenueAccountId`) مخصَّص فقط لتسريع إدخال سطور فواتير المبيعات عبر combo-box بحث
  + إنشاء سريع، دون أي علاقة بمنطق حركات المخزون. هذا قرار نطاق: صناديق فواتير الشراء
  والمردودات مستقبلاً قد تحتاج قراراً مماثلاً منفصلاً، غير مشمول هنا عمداً.
- **فصل "حفظ كمسودة" عن "حفظ وترحيل":** أُضيف `post: boolean` (افتراضه `true` للتوافق مع
  الفواتير القديمة) لـ `createSalesInvoice` — مسار المسودة يتخطى إنشاء القيد المحاسبي
  بالكامل (لا معاملة `$transaction`، لا `createJournalEntryTx`) ويُنشئ الفاتورة مباشرةً
  بحالة `draft`. التعديل والحذف يبقيان مسموحين فقط للمسودات (نفس القاعدة القديمة)، والترحيل
  يمر عبر `POST /:id/post` الموجود أصلاً.
- **ربط/فك ربط فاتورة بسند قبض بعد الإنشاء (وليس فقط وقت إنشاء السند):** الكود القديم كان
  يسمح بتوزيع سند القبض على فواتير فقط لحظة إنشائه. أُضيفت قدرة حقيقية جديدة للـ backend:
  `POST /receipts/:id/allocations` (إضافة تخصيص لسند موجود) و
  `DELETE /receipts/:id/allocations/:invoiceId` (فك تخصيص). كلاهما يُعيد بناء القيد المحاسبي
  للسند بالكامل (حذف القديم + إنشاء جديد بالإجمالي المحدَّث عبر `repostReceiptEntryTx`) بدل
  محاولة تعديل قيد قائم جزئياً. **قاعدة حماية متعمّدة:** فك آخر تخصيص متبقٍ في سند مرفوض
  صراحةً برسالة توضّح أن الإجراء الصحيح هو حذف السند نفسه (بعد فك ترحيله)، لأن سند قبض بلا
  أي تخصيص لا معنى له. فاتورة واحدة قد ترتبط بأكثر من سند (سداد على دفعات من سندات مختلفة)،
  وسند واحد قد يُخصَّص لأكثر من فاتورة — الواجهة تدعم الحالتين معاً.
- **"فك الترحيل" نمط حذف كامل للقيد (لا نمط رجوع لمسودة):** اتساقاً مع بقية النظام (فواتير/
  سندات)، فك ترحيل فاتورة مبيعات يحذف قيدها المحاسبي بالكامل عبر `deleteJournalEntryTx` بدل
  مجرّد تحويله لحالة مسودة — إعادة الترحيل لاحقاً تُنشئ قيداً جديداً من الصفر.
- **نافذة الإنشاء Modal فوق القائمة، لا شاشة منفصلة:** بعد توضيح المستخدم صراحةً (تعديل
  لاحق على الطلب الأصلي)، `InvoiceFormModal.jsx` يُستدعى من `InvoicesTab.jsx` كنافذة طافية
  تُغلَق تلقائياً وتُحدِّث الجدول فوراً بعد الحفظ — بلا أي تنقّل بين مسارات.
- **إضافة عميل/صنف جديد من داخل نافذة الفاتورة (نافذة متداخلة فوق نافذة الفاتورة):**
  `NewCustomerModal.jsx` و`NewSellableItemModal.jsx` نافذتان فرعيتان تُفتحان فوق
  `InvoiceFormModal` دون إغلاقه أو فقدان أي بيانات مُدخَلة فيه (السطور الأخرى، العميل
  المختار سابقاً، إلخ) — عند الحفظ تُغلَق النافذة الفرعية فقط ويُملأ الحقل المعني تلقائياً
  بالعنصر الجديد. للتمييز البصري المطلوب صراحةً ("النافذة الفرعية فوق نافذة الفاتورة")، أُضيف
  صنف CSS `.nested-modal-overlay` بتعتيم أقوى وظل/حدود أوضح على صندوقها، مع الاعتماد على
  ترتيب `z-index` الطبيعي بين الطبقات (نافذة الفاتورة أدنى من نافذة العرض/الطباعة، وكلتاهما
  أدنى من النوافذ الفرعية ونوافذ التأكيد) بدل إجبار قيمة عشوائية.
- **النسخ (Duplicate) يُعامَل كإنشاء مسبق التعبئة، لا كمسار منفصل:** لا يوجد كيان أو حالة
  "نسخة" وسيطة — `InvoiceFormModal` نفسه يُستدعى في وضع الإنشاء مع بيانات ابتدائية (العميل
  والسطور) من الفاتورة المصدر، بتاريخ اليوم ورقم فاتورة جديد يُولَّد من الخادم تلقائياً. لا
  تُلمَس الفاتورة الأصلية إطلاقاً — العملية بأكملها إضافة صرفة، لا تعديل.
- **تعديل/حذف فاتورة مرحّلة:** يُمنعان صراحةً بنافذة تنبيه (`PostedBlockModal.jsx`) تشرح
  السبب وتوفّر زر "فك الترحيل" مباشرةً داخل نفس التنبيه (بدل إجبار المستخدم على البحث عن
  الأيقونة في صف الإجراءات) — بعد فك الترحيل تتحول الفاتورة لمسودة تلقائياً ويمكن عندها
  المتابعة. أيقونة "فك الترحيل" المباشرة تبقى موجودة أيضاً في صف الإجراءات لنفس الغرض دون
  المرور بمسار التعديل/الحذف أولاً.

### خطأ حقيقي اكتُشف وأُصلح أثناء الاختبار الفعلي (وليس مجرد تخمين)

اختبار المتصفح الكامل (أدناه) كشف أن إنشاء فاتورة بسطر لا يحمل صنفاً مُختاراً من الكتالوج
(أي وصف حر بلا `sellableItemId` — حالة مشروعة تماماً ومذكورة صراحة في واجهة السطر: "اكتب اسم
الصنف أو وصفاً حراً") كان يفشل بخطأ `409` من قاعدة البيانات (انتهاك قيد مفتاح أجنبي)، لأن
الواجهة كانت ترسل `sellableItemId: ""` (سلسلة فارغة) بدل حذف الحقل، ومحاولة Prisma ربط سطر
الفاتورة بصنف معرّفه سلسلة فارغة تفشل حتماً. الإصلاح في مخطط Zod الخاص بفواتير المبيعات:
تحويل أي `sellableItemId` فارغ إلى `undefined` قبل الوصول للخدمة، بحيث يبقى الحقل بلا قيمة
فعلياً في قاعدة البيانات كما يُفترض لسطر بلا صنف مرتبط.

### كيف اختُبرت الميزة فعلياً (متصفح حقيقي عبر Playwright، تسجيل مستخدم فعلي عبر الـ API ثم
قيادة الواجهة الحقيقية بالكامل)

سيناريو واحد متصل يغطي: إنشاء فاتورة عبر النافذة المنبثقة مع اختبار **كلتا** النافذتين
الفرعيتين فعلياً (كتابة اسم عميل غير موجود → "+ إضافة عميل جديد باسم..." → نافذة فرعية →
حفظ → عودة لنافذة الفاتورة بنفس العميل مُختاراً تلقائياً وبلا فقدان بيانات؛ ثم نفس الشيء لصنف
غير موجود داخل سطر الفاتورة)، حفظ كمسودة، فتح المسودة للتعديل مباشرة (بلا حاجز)، حفظ وترحيل
(والتأكد من نص التوست يذكر إنشاء القيد فعلاً)، محاولة تعديل فاتورة مرحّلة (تأكيد ظهور حاجز
"فك الترحيل" الإلزامي، فك الترحيل من داخل نفس الحاجز بالرقم السري الفعلي، تأكيد رجوعها
مسودة، ثم إعادة ترحيلها)، عرض الفاتورة للقراءة فقط والطباعة (كلا الأيقونتين تفتحان نفس شاشة
العرض/الطباعة الحقيقية بها QR زاتكا)، عرض القيد المحاسبي المرتبط، ربط الفاتورة بسند قبض
جديد بالكامل، محاولة فك ربط **التخصيص الوحيد** في سند (تأكيد الرفض الصريح المطلوب)، إنشاء
فاتورة ثانية وربطها بنفس السند القائم (سند بتخصيصين الآن)، فك ربط الفاتورة الأولى بنجاح فعلي
هذه المرة (حالة السداد ترجع "غير مسددة" فوراً في الجدول)، نسخ فاتورة مرحّلة (فاتورة جديدة
برقم مختلف وتاريخ اليوم كمسودة، والأصلية تبقى مرحّلة بلا أي تغيير)، حذف المسودة المنسوخة
مباشرة، محاولة حذف فاتورة مرحّلة (تأكيد حاجز الحذف بنفس منطق حاجز التعديل)، وأخيراً التأكد أن
أيقونة "عرض القيد" مُعطَّلة فعلياً (`disabled`) على فاتورة مسودة. **33 فحصاً تلقائياً، كلها
نجحت.** كل نص توست تحقّق منه الاختبار قُرئ من الـ DOM الفعلي بعد انتظار تغيّر محتواه (لا قراءة
توست متبقٍ من فعل سابق)، وكل استجابة HTTP فاشلة أثناء الاختبار سُجِّلت ليتضح أن الفشل الوحيد
الحقيقي كان الخطأ المذكور أعلاه (قبل إصلاحه)، وأن الرفض اللاحق لفك تخصيص وحيد كان سلوكاً
صحيحاً متعمَّداً لا عطلاً.

## بيانات الشركة الرسمية الكاملة + تعبئة تلقائية بالذكاء الاصطناعي + هيدر/فوتر موحّد لكل المطبوعات

توسيع كبير لشاشة "بيانات الشركة": حقول رسمية كاملة (سجل تجاري بتاريخي إصدار/انتهاء، عنوان
وطني ببنوده الستة، بريد/هاتف رسمي، شعار)، استخراج تلقائي لهذه الحقول من مستندات مرفوعة عبر
نفس آلية الرؤية بالذكاء الاصطناعي المستخدَمة أصلاً لإنشاء القيود من المستندات، وأخيراً هيدر/
فوتر موحّد يظهر إلزامياً في **كل** مطبوعات النظام.

### القرارات التصميمية

- **حقول العنوان الوطني منفصلة (لا نص حر واحد):** استُبدل `Company.nationalAddress` (نص حر
  واحد) بستة أعمدة منفصلة (`addressBuilding/Street/District/City/PostalCode/AdditionalNo`)
  — مطابقة تماماً لبنود العنوان الوطني السعودي الرسمية، وتسمح لكل من الاستخراج بالذكاء
  الاصطناعي والعرض المختصر/الكامل في المطبوعات بالتعامل مع كل بند على حدة.
- **الشعار: `logoKey` داخلياً + `logoUrl` مؤقت عند كل طلب:** بنفس منطق `Attachment.fileKey`
  الموجود مسبقاً — لا يُخزَّن أي رابط دائم؛ `POST /companies/:id/logo` يرفع الملف عبر نفس
  عميل R2/S3 المستخدَم للمرفقات، ويُعاد حساب رابط presigned صالح لساعة في كل استجابة
  (`listCompanies`/`createCompany`/`updateCompany`/رفع الشعار نفسه) عبر دالة `withLogoUrl`.
- **استخراج بيانات الشركة مبني على نفس نمط `extractJournalEntryFromDocument` حرفياً** (نفس
  تقنية الـ prefill، نفس بنية استدعاء Anthropic Messages API)، لكن بدالة جديدة
  `extractCompanyDataFromDocument(buffer, mimeType, docType)` تُخصِّص الـ prompt والحقول
  المطلوبة حسب `docType` (`cr`/`national_address`/`vat_certificate`) بدل شجرة الحسابات —
  لأنه لا يوجد هنا "قائمة مسموحة" شبيهة بالحسابات يُتحقَّق الاقتراح مقابلها، فالتحقق الوحيد
  الممكن هو تصنيف كل حقل مُعاد كنص أو تجاهله (`typeof === "string"`)، مع طلب صريح من
  النموذج نفسه لتقييم وضوح المستند (`confidence: "high"|"low"` + `confidenceNote`) بدل
  الاعتماد على استدلال آلي (عدد الحقول الفارغة مثلاً) لتحديد الثقة.
- **الاستخراج لا يحفظ شيئاً في `Company` مباشرة — فقط يُعيد `fields` للمراجعة:** يطابق
  الشرط الصريح "معاينة قبل الحفظ" — الواجهة تدمج `fields` المُستخرَجة في نفس حقول الفورم
  (القابلة للتعديل) دون أي نداء `PATCH` تلقائي؛ فقط زر "حفظ" الصريح من المستخدم يكتب
  البيانات فعلياً. عند فشل الاستخراج أو ضعف الثقة، `fields` تُعاد فارغة مع `confidenceNote`
  توضيحية تُعرَض للمستخدم كرسالة تحذير بدل ملء الفورم ببيانات قد تكون خاطئة بصمت.
  - **المستند الأصلي يُؤرشَف دائماً بصرف النظر عن نجاح الاستخراج:** الـ handler يرفع الملف
    كـ `Attachment` (بعد إضافة `"company"` لقائمة `attachmentEntityTypeEnum` الموجودة) أولاً،
    ثم يحاول الاستخراج داخل `try/catch` منفصل — فشل الاستخراج (حتى خطأ 500 من عدم ضبط
    `ANTHROPIC_API_KEY`) لا يُفقِد المستند المرفوع، فقط يُعاد بثقة منخفضة ورسالة الخطأ نفسها
    كـ `confidenceNote`.
- **كشف حساب (Statement of Account) جديد كلياً على مستوى الـ backend:** لم يكن موجوداً حتى
  كواجهة API قبل هذا التسليم. `getCustomerStatement`/`getSupplierStatement` في موديول
  `reports` يبنيان سجل حركة + رصيد متحرك **من أسطر القيود على حساب الذمم فقط** ("ذمم مدينة"
  للعميل، "ذمم دائنة - موردين" للمورد؛ نفس الأسماء المستخدَمة في `getCustomerBalance` في
  موديول العملاء) — أسطر الإيراد/المصروف والضريبة في نفس القيد مُستبعَدة عمداً رغم أنها
  موسومة بنفس `customerId`/`supplierId`، لأنها ليست جزءاً من حركة حساب الذمم نفسه وستُكرّر
  المبلغ لو أُدرِجت. إشارة الرصيد معكوسة بين العميل (مدين الطبيعة) والمورد (دائن الطبيعة).
- **الهيدر/الفوتر المشترَكان أُضيفا داخل `PrintShell` نفسه** (لا مكوّن منفصل جديد) لأنه
  نقطة الدخول الوحيدة الفعلية لكل شاشات الطباعة الحالية والمستقبلية في هذا الكود — أي تعديل
  عليهما لاحقاً يسري تلقائياً على كل مطبوعة. الهيدر يعرض الاسم التجاري (أو الاسم في السجل
  لو التجاري غير موجود) + الرقم الضريبي + عنوان مختصر (شارع، حي، مدينة) مبنيّ من الحقول
  المنفصلة عبر `formatCompanyAddress`. الفوتر يعرض اسم المستخدم الحالي (`useAuth()`، متاح
  داخل `PrintShell` لأنه يُركَّب دوماً ضمن شجرة `AuthProvider` رغم استخدام `createPortal`)
  ووقت الطباعة الفعلي — يُلتقَط في `state` عند الضغط الفعلي على "طباعة"/"تحميل PDF" (لا وقت
  فتح النافذة)، مع تأخير 30ms قبل استدعاء `window.print()` ليضمن تحديث الفوتر في الـ DOM أولاً.
- **بيانات الشركة المعروضة في الهيدر تُقرَأ من قائمة الشركات المُحمَّلة فعلياً على مستوى
  التطبيق (`companies` prop)، لا من الكائن المضمَّن داخل الفاتورة/القيد نفسه:** الكائنات
  المضمَّنة (`invoice.company` مثلاً عبر `include: { company: true }`) تحمل `logoKey` الخام
  غير المحوَّل لرابط صالح (التحويل يحدث فقط داخل موديول `companies` نفسه)، وتعكس بيانات
  الشركة **وقت إصدار المستند** لا الحالية. استخدام القائمة الحية بدلاً منها أصلح تقنياً (رابط
  شعار صالح دائماً) ومنطقياً أصح محاسبياً (الترويسة تعرض هوية الشركة الحالية، كأي ورقة رسمية
  حقيقية بترويسة مطبوعة مسبقاً وليست لقطة تاريخية).
- **شاشات طباعة جديدة كلياً لم تكن موجودة أصلاً قبل هذا التسليم:** فواتير المشتريات (أيقونتا
  عرض/طباعة في القائمة، بدون أي إعادة تصميم للشاشة نفسها — خارج النطاق)، سند القيد المحاسبي
  من شاشة القيود اليومية مباشرة، التقارير المالية الثلاثة (زر طباعة واحد يطبع التقرير النشط
  حالياً بنفس بياناته المعروضة على الشاشة)، وكشف الرواتب (أفقي — يُعاد استخدام صنف
  `wide-payroll-table` الموجود مسبقاً في CSS الطباعة).

### كيف اختُبرت الميزة فعلياً (متصفح حقيقي + خادمان محليّان بديلان لـ R2 وAnthropic)

بيئة هذه الجلسة لا تملك بيانات اعتماد R2 أو `ANTHROPIC_API_KEY` حقيقية، فتم تشغيل بديلين
حقيقيين محليّين (كما في اختبار المرحلة السابقة): خادم `s3rver` فعلي لتخزين الشعار والمرفقات
(تم فعلياً رفع شعار PNG والتأكد من مطابقة بايتاته بايتاً لبايت عبر الرابط المؤقَّت المُعاد)،
وخادم HTTP وهمي بنفس شكل استجابة Anthropic Messages API بالضبط (بما فيها تقنية الـ prefill)
يُرجِع بيانات سجل تجاري وهمية بثقة عالية. سيناريو Playwright واحد متصل غطّى: فتح نافذة تعديل
بيانات الشركة، تعبئة حقول رسمية يدوياً، رفع شعار حقيقي والتأكد من ظهور معاينته، رفع "مستند
سجل تجاري" وهمي والتأكد أن حقول الاسم/رقم السجل امتلأت تلقائياً من استجابة الخادم الوهمي
ورسالة الثقة ظهرت، التأكد أن المستند نفسه ظهر في لوحة المرفقات، حفظ ثم إعادة فتح النافذة
والتأكد من بقاء رقم السجل والشعار بعد إعادة التحميل (بيانات حقيقية من قاعدة البيانات، لا
حالة محلية)، إنشاء عميل وفاتورة مبيعات مرحّلة فعلياً ثم فتح عرض/طباعة الفاتورة والتأكد أن
هيدرها يحمل الرقم الضريبي والعنوان الصحيحين وأن فوترها يحمل اسم المستخدم الحالي ووقت
طباعة فعلي، فتح كشف حساب لنفس العميل والتأكد من ظهور حركة الفاتورة والمبلغ الصحيح، إنشاء
مورد وفاتورة مشتريات مرحّلة والتأكد من ظهور نفس الهيدر الصحيح في طباعتها، إنشاء قيد يومية
متوازن يدوياً والتأكد من ظهور نفس الهيدر/الفوتر في طباعته، وأخيراً فتح طباعة ميزان المراجعة
من شاشة التقارير المالية والتأكد من ظهور نفس هيدر الشركة فيه أيضاً. **20 فحصاً تلقائياً، كلها
نجحت.**

## إصلاح خطأ 400 "assistant message prefill" في استخراج المستندات بالذكاء الاصطناعي

بعد النشر، ظهر خطأ حقيقي من Anthropic API عند رفع أي مستند رسمي: `400` —
`"This model does not support assistant message prefill. The conversation must end with
a user message."`. السبب: كلتا الدالتين في `src/lib/claudeVision.ts`
(`extractJournalEntryFromDocument` و`extractCompanyDataFromDocument`) كانتا تنهيان مصفوفة
`messages` برسالة `{role: "assistant", content: "{"}` لإجبار الرد على البدء بـ JSON خالص —
تقنية لا يدعمها النموذج المستخدَم فعلياً في الإنتاج.

**الإصلاح المطبَّق:** استبدال الـ prefill بالكامل بـ **Tool Use** (استدعاء أداة إجباري عبر
`tool_choice: { type: "tool", name: "..." }`) في كلتا الدالتين، عبر دالة مشتركة جديدة
`callAnthropicVisionTool`. هذا الخيار (لا التنظيف اليدوي لعلامات ```` ```json ```` من نص حر)
لأن Anthropic تُعيد `tool_use.input` كـ JSON مُوثَّق (`object`) مُطابِق فعلياً لمخطط
(`input_schema`) مُرسَل مسبقاً — فلا حاجة لأي تحليل نص خام أو regex لاستخراج حدود `{}` (تمت
إزالة `extractJsonBlock` القديمة بالكامل)، ومحادثة تنتهي دائماً برسالة `user` واحدة فقط، وهو
ما يعمل مع أي نموذج يدعم استدعاء الأدوات بصرف النظر عن دعمه لـ prefill من عدمه. **لم يتغيّر
النموذج (`ANTHROPIC_MODEL`) نفسه إطلاقاً** — الإصلاح في طريقة بناء الطلب فقط لا في اختيار
النموذج، فلا أثر على التكلفة.

**تحسين إضافي أتاحه Tool Use نفسه:** حسابات القيد المقترحة (`suggested_debit_account_id`/
`suggested_credit_account_id`) أصبحت مُقيَّدة بـ `enum` داخل مخطط الأداة بقيم معرّفات شجرة
الحسابات الفعلية لهذا المستأجر — بنيوياً لا يمكن للنموذج إرجاع معرّف حساب غير موجود أصلاً، بدل
الاعتماد فقط على التحقق البرمجي اللاحق (الذي بقي كما هو أيضاً كطبقة حماية إضافية).

نفس الدالة المشتركة (`callAnthropicVisionTool`) تُستخدَم من كلا الاستدعاءين في النظام —
إنشاء القيود من المستندات (`journalEntries.service.ts`) واستخراج بيانات الشركة الرسمية
(`companies.controller.ts`) — فالإصلاح في `claudeVision.ts` وحده كافٍ لكلتا الميزتين دون أي
تعديل في الموديولين المستدعيين (تحقّقتُ بالبحث في الكود أن `claudeVision.ts` هو المكان الوحيد
في `src/` الذي يستدعي Anthropic API إطلاقاً).

**كيف اختُبر الإصلاح فعلياً:** حُدِّث الخادم الوهمي المحلي (البديل عن Anthropic الحقيقي في هذه
البيئة) ليحاكي شكل استجابة Tool Use الحقيقي (`content: [{type: "tool_use", input: {...}}]`)
بدل نص الـ prefill القديم، ثم رُفعت فعلياً عبر واجهة المستخدم الحقيقية (متصفح Playwright) كل
المستندات الثلاثة المطلوبة (سجل تجاري برقم 7007192524، عنوان وطني بجدة، شهادة ضريبة القيمة
المضافة) والتُقطت شاشات تُظهر امتلاء الحقول الصحيحة تلقائياً بلا أي رسالة خطأ 400/prefill، مع
تأكيد إضافي عبر استدعاء مباشر لنقطة نهاية `POST /journal-entries/from-document` للتأكد أن
ميزة إنشاء القيود من المستندات (المستخدِمة لنفس المكتبة) تعمل بنفس الإصلاح أيضاً. **كل
الفحوصات نجحت.**

## إعادة تصميم آلية اختيار/تبديل الشركة (Active Company Context)

قبل هذه المرحلة، كانت كل شاشة معاملات (فواتير المبيعات، المشتريات، المخزون...) تعرض بنفسها
قائمة منسدلة "الشركة (بيانات حقيقية)" + زر "+ شركة جديدة" مجاور لها أعلى الشاشة، فيضطر
المستخدم لاختيار الشركة من جديد في كل شاشة يفتحها. الطلب: نقل اختيار "الشركة النشطة" إلى مكان
واحد مركزي في الشاشة الرئيسية (Dashboard)، على هيئة أيقونة/بطاقة منفصلة لكل شركة في المجموعة
+ أيقونة إضافية "المجموعة كاملة" لعرض مُجمَّع، وحذف القائمة المنسدلة والزر نهائياً من كل شاشات
المعاملات، مع نقل إنشاء شركة جديدة بالكامل إلى الإعدادات ← بيانات الشركات.

### القرارات التصميمية

- **لا حاجة لبنية جديدة لـ"السياق النشط"**: بالفحص وُجد أن مفهوم "الشركة النشطة عبر كامل
  التطبيق" كان موجوداً فعلياً بشكل ضمني — الخطاف المشترك `useCompanies()` في `App.jsx` كان
  بالفعل هو المصدر الوحيد لـ `companyId` المُمرَّر لكل الوحدات ("Wired modules")، فقط لم يكن
  ذلك الاختيار مثبَّتاً (persisted) عبر عمليات إعادة التحميل، ولم تكن هناك نقطة دخول مركزية
  واحدة له. لذلك لم تكن إعادة البناء تتطلب معمارية جديدة تمس أجزاء كثيرة من النظام، بل فقط:
  (1) نقل نقطة الاختيار من كل شاشة إلى الشاشة الرئيسية، (2) تثبيت الاختيار في `localStorage`
  بمفتاح خاص بكل مستأجر (`athar.activeCompanyId.<tenantId>`) لمنع تسرّب اختيار شركة مستأجر إلى
  آخر عند تسجيل الدخول بمستأجر مختلف على نفس المتصفح، (3) عرضه في الشريط العلوي.
- **"المجموعة كاملة" مُنجزة بدون أي نقطة نهاية تجميع جديدة في الباك-إند**: نقاط نهاية التقارير
  المالية الحالية (`getTrialBalance`/`getIncomeStatement`/`getBalanceSheet`) كانت أصلاً تدعم
  حذف مرشّح `companyId`، فتُرجِع تلقائياً بيانات كل شركات المستأجر مجمَّعة. لذلك بُنيت شاشة
  "المجموعة كاملة" في الواجهة الأمامية فقط كواجهة تجلب بيانات كل شركة على حدة بالتوازي (نفس
  نقاط النهاية المستخدَمة أصلاً لكل شركة) ثم تجمعها وتعرضها في جدول مقارنة، دون أي تعديل خلفي.
  اختيار "المجموعة كاملة" يُغيّر فقط حالة عرض محلية (`viewMode`) في `Dashboard.jsx` ولا يُغيّر
  إطلاقاً "الشركة النشطة" الحقيقية (`companyId`) المستخدَمة في بقية شاشات النظام — أي شاشة
  أخرى غير لوحة القيادة تعمل دوماً على شركة واحدة محددة فعلياً، أبداً على "الكل".
- **فرض صلاحيات الوصول لأول مرة فعلياً على `companyScope`**: حقل `companyScope` في نموذج
  `User` (مُضمَّن في الـ JWT، قيمته إما `"all"` أو معرّف شركة محددة) كان موجوداً في المخطط منذ
  مراحل سابقة لكن **بلا أي نقطة إنفاذ فعلية** في الباك-إند بأكمله (بحث في الكود أكد صفر
  استدعاءات للدالة المساعدة `assertCompanyAccess` في أي مكان). لتلبية شرط "أيقونات لوحة
  القيادة يجب ألا تُظهر إلا الشركات المصرَّح للمستخدم بها"، عُدِّل `listCompanies` في
  `companies.controller.ts` ليُرشِّح النتائج بحسب `companyScope` مباشرة. تعمّدت عدم التوسّع في
  تدقيق أمني شامل لكل نقاط النهاية الأخرى المرتبطة بشركة (خارج نطاق الطلب المباشر)، واكتفيت
  بنقطة الإنفاذ الوحيدة المطلوبة فعلياً لهذه الميزة.
- **إنشاء الشركة أصبح مُتاحاً حصراً من الإعدادات**: زر "+ شركة جديدة" انتقل بالكامل إلى
  `CompaniesSettings.jsx` (مكوّن جديد `NewCompanyForm`)، وحُذف مكوّن `CompanySelector.jsx` نفسه
  نهائياً من المشروع بعد التأكد (بالبحث) أن لا شاشة تستورده بعد إزالته من الشاشات السبع
  (المبيعات، المشتريات، المخزون، الأصول الثابتة، شؤون الموظفين، التقارير، القيود اليومية).

### خطأ حقيقي اكتُشف وأُصلح أثناء الاختبار الفعلي (وليس مجرد تخمين)

أثناء اختبار نموذج "+ شركة جديدة" الجديد عبر Playwright، ظهر عطل غريب: زر "إنشاء الشركة" كان
**مرئياً فعلياً على الشاشة** (تؤكده لقطات الشاشة) لكن `page.getByRole("button", { name:
"إنشاء الشركة" })` كان يُرجِع صفر عناصر مطابقة رغم أن الزر موجود في الـ DOM
(`querySelectorAll` العادي كان يجده بلا مشكلة). التشخيص كشف السبب الجذري: الزر كان ملفوفاً
بعنصر `<label>` (بدل `<div>`) اسْتُخدِم فقط كحيلة تنسيق (`alignSelf: "end"`) منسوخة عن حقول
الإدخال المجاورة له — وهذا CSS/markup غير صحيح دلالياً (استخدام `<label>` لعنصر لا يُصنِّف أي
حقل إدخال) أفسد حساب "الاسم المتاح لإمكانية الوصول" (accessible name) للزر داخل شجرة
الوصولية، فأصبح غير قابل للاستهداف بمُحدِّد الدور (`role=button`) رغم ظهوره البصري السليم.
الإصلاح: استبدال `<label>` بـ `<div>` عادي في `CompaniesSettings.jsx`. هذا خطأ إتاحة وصول
(accessibility) حقيقي كان سيُصعِّب على قارئات الشاشة أيضاً التعرّف على الزر، وليس مجرد عيب في
سكربت الاختبار.

### كيف اختُبرت الميزة فعلياً (متصفح حقيقي عبر Playwright، تسجيل مستأجر تجريبي جديد فعلياً عبر
واجهة الـ API الحقيقية، لا بيانات وهمية)

سيناريو Playwright واحد شامل غطّى: (1) حالة "لا توجد شركات بعد" على لوحة القيادة لمستأجر جديد
تماماً، (2) الانتقال من زر الحالة الفارغة إلى الإعدادات وإنشاء شركتين حقيقيتين من هناك فقط،
(3) التأكد أن جدول الإعدادات لا يحوي أي `<select>` إطلاقاً، (4) ظهور بطاقتي أيقونة (شركة لكل
شركة) + بطاقة "المجموعة كاملة" واحدة بالضبط على لوحة القيادة، (5) نقر بطاقة الشركة الأولى
وتأكيد التظليل الذهبي + ظهور اسمها في الشريط العلوي، (6) التأكد أن شاشة فواتير المبيعات لا
تحوي أي قائمة منسدلة للشركة ولا نص "الشركة (بيانات حقيقية)" القديم، ثم إنشاء فاتورة فعلية
مرتبطة بالشركة الأولى، (7) التبديل إلى الشركة الثانية من لوحة القيادة والتأكد أن قائمة فواتيرها
منفصلة تماماً (فارغة) عن فواتير الأولى، (8) إعادة تحميل الصفحة (`page.reload()`) والتأكد أن
الشركة النشطة (الثانية) بقيت محفوظة في الشريط العلوي ولم ترجع لأول شركة، (9) فتح "المجموعة
كاملة" والتأكد من ظهور جدول مقارنة يضم الشركتين + أن "الشركة النشطة" الحقيقية في الشريط العلوي
لم تتغيّر رغم فتح هذا العرض. **كل الفحوصات التسعة عشر نجحت.**

## داشبوردان احترافيان جديدان: الداشبورد المالية الرئيسية وداشبورد شئون الموظفين

طُلب بناء داشبورد مالية شاملة (مؤشرات سريعة، رسوم بيانية للمبيعات/الكاش/المركز المالي، تنبيهات
ذكية) وداشبورد مخصصة لشئون الموظفين (مؤشرات القوى العاملة، توزيعات، تنبيهات)، كلتاهما تحترمان
"الشركة النشطة" مع خيار "عرض المجموعة كاملة" المُتّفَق عليه في المرحلة السابقة.

### نقاط تم توضيحها مع المستخدم قبل البدء (بحث + أسئلة صريحة)

بحث في الكود قبل الكتابة كشف عدة فجوات بيانات حقيقية طُرحت على المستخدم صراحةً بدل افتراضها:

1. **لا توجد مكتبة رسوم بيانية مثبَّتة أصلاً** (الداشبورد القديمة كانت SVG يدوي بسيط
   Gauge/Donut فقط) — اختار المستخدم إضافة **recharts**.
2. **سندات القبض البنكية كانت تُثبّت حساباً بنكياً واحداً بالكود** (`CREDIT_ACCOUNT_NAME.bank`
   في `receipts.service.ts`)، فلن يعكس رسم "توزيع الكاش على البنوك" الواقع إن أضفنا حسابات بنوك
   أخرى — اختار المستخدم **إصلاح هذا الآن**.
3. **أربعة عناصر تنبيهات مطلوبة لا بنية بيانات لها إطلاقاً حالياً** (عقود الإيجار، موعد ضريبة
   القيمة المضافة، التزامات الزكاة، فترة التجربة بدون تقييم) — اختار المستخدم **بناء الأربعة**،
   وأضاف طلباً خامساً بصيغة حرة: تعميم تنبيهات المستندات الإدارية (تراخيص بلدية، سجلات تجارية،
   عقود أمن وسلامة) وعقود الموظفين.

### قرارات تصميمية

- **شجرة الحسابات مشتركة على مستوى المستأجر لا الشركة** (`Account` بلا `companyId`، تُفصَل
  الأرصدة فقط عبر `companyId` في `JournalEntry`) — هذا يعني أن "عرض المجموعة كاملة" لكل نقاط
  نهاية الداشبورد يُنجَز ببساطة **بحذف `companyId` من الاستعلام نفسه** فيُصبح تجميعاً تلقائياً
  عبر كل شركات المستأجر، دون أي كود تجميع منفصل أو نقطة نهاية جديدة للمجموعة.
- **حساب "نقدي/بنكي" أصبح تصنيفاً صريحاً لا تخميناً بالاسم**: أُضيف حقل `isBankOrCash` على
  `Account` (بدل تخمين "البنك"/"النقدية" من نص الاسم، وهو هش وينكسر مع أي بنك جديد مثل الراجحي/
  ساب/الإنماء) — يُفعَّل يدوياً عند إضافة/تعديل حساب من شجرة الحسابات، ويُغذّي كلاً من رسم توزيع
  الكاش ورصيد الكاش الإجمالي ومحدد "الحساب البنكي" في سند القبض.
- **إصلاح سندات القبض البنكية**: أُضيف `bankAccountId` اختياري على `Receipt` + دالة موحّدة
  `resolveCreditAccountId` في `receipts.service.ts` تُرحِّل للحساب المُختار صراحةً عند التحصيل
  البنكي (بعد التأكد أنه فعلاً `isBankOrCash` ضمن نفس المستأجر)، أو تتراجع للحساب الافتراضي
  القديم إن لم يُحدَّد (**توافق كامل مع السندات القديمة**، لا حاجة لـ migration بيانات).
- **"نسبة التداول" في المركز المالي تقريبية معلنة، لا حقيقية**: شجرة الحسابات لا تُصنِّف الأصول/
  الالتزامات إلى "متداول/غير متداول" حالياً، فاستُخدِم (الكاش + الذمم المدينة) ÷ الذمم الدائنة
  كتقريب عملي — موضَّح صراحة في الواجهة بنجمة (*) بدل الادّعاء بدقة غير متوفرة فعلياً. نسبة
  الديون لحقوق الملكية (`debtToEquity`) دقيقة تماماً لأنها لا تحتاج هذا التصنيف.
- **مخصص نهاية الخدمة في KPI تقدير Provision لا تصفية فعلية**: يُحسب بافتراض إنهاء عادي من صاحب
  العمل اليوم لكل موظف نشط (`calcEOS(..., "employer")`، النسبة = ١ دائماً)، فلا يُطبَّق خصم نسبة
  الاستقالة (المادة ٨٥) — موضَّح في هامش الشاشة، ويُعاد استخدام دالة `calcEOS` الموجودة أصلاً بدل
  منطق حساب جديد.
- **موعد ضريبة القيمة المضافة قاعدة محسوبة لا تقويم مُخزَّن**: أُضيف حقل واحد فقط
  `vatFilingFrequency` (شهري/ربع سنوي) على `Company`، ويُحسَب "الموعد النهائي القادم" حسابياً في
  `dashboard.service.ts` (نهاية الشهر الحالي للشهري، أقرب ٣٠ إبريل/٣١ يوليو/٣١ أكتوبر/٣١ يناير
  للربع سنوي) — بدل تخزين تقويم ضريبي كامل غير مطلوب فعلياً.
- **تعميم `CompanyDocument`**: الجدول كان موجوداً في المخطط منذ مرحلة سابقة لكن بلا أي API — أُضيف
  موديول `companyDocuments` CRUD كامل يغطي أي نوع مستند إداري (رخصة بلدية، دفاع مدني، عقد أمن
  وسلامة...)، تماماً كطلب المستخدم بصيغته الحرة.
- **`LeaseContract` نموذج جديد بالكامل** (لم يكن موجوداً إطلاقاً) — الحد الأدنى من الحقول
  (العنوان، المؤجِّر، الإيجار الشهري، تاريخا البداية والنهاية) الكافي لتغذية تنبيه "عقد إيجار
  قارب على الانتهاء" دون تعقيد إضافي غير مطلوب.
- **عتبات التنبيهات القابلة للتخصيص محفوظة لكل شركة، والباقي محسوب وقت العرض**: `Company` اكتسب
  `lowCashThreshold`/`overdueInvoiceDays`/`staleDraftDays` كحقول مُعدَّة من الإعدادات (لأن
  المستخدم طلب صراحة أن تكون "قابلة للتحديد لكل شركة")، بينما تنبيهات أخرى (عقود الإيجار، انتهاء
  المستندات) تستخدم مُعامِل `withinDays` وقت الاستعلام (مطابقة لنمط `expiringDocumentsHandler`
  الموجود أصلاً في تقارير الموارد البشرية) دون حقل تخزين مخصص لكل نوع.
- **الرسوم البيانية بألوان النظام لا ألوان recharts الافتراضية**: ملف `chartTheme.js` مشترك بين
  الداشبوردين يُعيد استخدام نفس لوحة الألوان الموجودة (ذهبي #B98B4E، كحلي #10202E، أخضر
  زيتوني #2F5D5A للإيجابي، أحمر طوبي #A8432B للسلبي) بدل الألوان الافتراضية لأي مكتبة خارجية.

### خطأ حقيقي اكتُشف وأُصلح أثناء الاختبار الفعلي

أول تشغيل لسيناريو Playwright الكامل فشل بصمت: كل بطاقات KPI والرسوم البيانية كانت تُظهر
"جارٍ التحميل..." إلى الأبد بلا أي خطأ في الـ Console. السبب: مكوّن `PeriodFilter` الجديد كان
يُبلّغ بالفترة الزمنية المختارة (`onChange`) فقط عند نقر المستخدم على أحد أزرار الفترة، لا عند
التحميل الأول — فتبقى حالة `range` في `FinancialDashboard` قيمتها `null` إلى الأبد ما لم يتفاعل
المستخدم يدوياً، ويظل `useEffect` الذي يجلب كل بيانات الداشبورد (`if (!range) return;`) بلا أي
تنفيذ. الإصلاح: `useEffect` بسيط في `PeriodFilter` يستدعي `onChange` بالفترة الافتراضية ("الشهر
الحالي") فور التركيب. تأكيد أن الإصلاح صحيح جاء من تصوير الشاشة قبل وبعد: قبل الإصلاح كانت كل
البطاقات فارغة رغم أن مُرشِّح الفترة نفسه (الأزرار) يظهر بشكل سليم؛ بعده ظهرت خمس بطاقات KPI
وأربعة رسوم بيانية فوراً دون أي نقر من المستخدم.

### كيف اختُبرت الميزة فعلياً (متصفح حقيقي عبر Playwright، تسجيل مستأجر جديد فعلياً عبر واجهة
الـ API الحقيقية، بيانات حقيقية لا وهمية)

سيناريو Playwright واحد غطّى: (1) إنشاء شركة من الإعدادات، (2) ظهور ٥ بطاقات KPI + ودجت التنبيهات
+ ٤ رسوم بيانية على الأقل + مُرشِّح فترة بأربعة خيارات على الداشبورد المالية لشركة جديدة تماماً،
(3) ظهور تنبيه "موعد تقديم إقرار ضريبة القيمة المضافة" تلقائياً لشركة جديدة (يُحسَب من
`vatFilingFrequency` الافتراضي بلا أي إعداد يدوي)، (4) التبديل بين خيارات مُرشِّح الفترة الأربعة
دون أي عطل، بما فيها "فترة مخصصة" التي تُظهر حقلي تاريخ، (5) من الإعدادات: ضبط دورية ضريبة القيمة
المضافة شهرياً + حد أدنى للكاش + مدة تأخر الفاتورة، ثم إضافة عقد إيجار ينتهي خلال ٢٠ يوماً ومستند
إداري ("رخصة بلدية") ينتهي بنفس المدة، (6) التأكد من ظهور تنبيه "عقد إيجار قارب على الانتهاء" في
الداشبورد المالية بعد الحفظ مباشرة، (7) التأكد أن تبويب "الداشبورد" هو التبويب **الافتراضي
النشط** عند فتح قسم شئون الموظفين لأول مرة (لا "ملفات الموظفين" كما كان)، وظهور ٤ بطاقات KPI فيه،
(8) إنشاء موظف بتاريخ نهاية فترة تجربة **في الماضي** (قبل ١٠ أيام) بدون تفعيل "تم التقييم"، والتأكد
من ظهور تنبيه "تجاوز فترة التجربة بدون تقييم مسجّل" في داشبورد شئون الموظفين فوراً + تحديث مؤشر
"عدد الموظفين النشطين" إلى ١، (9) من شجرة الحسابات: إنشاء حساب بنكي جديد ("بنك الراجحي - حساب
تشغيلي") مع تفعيل خانة "حساب نقدي/بنكي" الجديدة، والتأكد أنه يظهر في القائمة بهذا التصنيف (جاهز
لسندات القبض البنكية ورسم توزيع الكاش). **كل الفحوصات الأربعة عشر نجحت.**

## إعادة تصميم القائمة الجانبية: Accordion حقيقي + أيقونات لكل عنصر

المشكلة المطلوب حلّها: الضغط على اسم القسم (مثلاً "المبيعات") كان يفتح القائمة الفرعية لكن لا
يقفلها — فقط أيقونة السهم كانت تملك منطق الإغلاق (`e.stopPropagation()` منفصل تماماً عن ضغط
الاسم) — ولم يكن هناك سلوك Accordion فعلي إطلاقاً: فتح قسمين معاً كان ممكناً لأن الحالة كانت
مصفوفة `openGroups: string[]` (كل قسم له عضوية مستقلة فيها)، لا قيمة واحدة.

### القرار التصميمي الجوهري: حالة واحدة مشتركة بدل مصفوفة

استُبدلت `openGroups` (مصفوفة) بـ `openGroupId` (قيمة واحدة أو `null`) على مستوى `AppShell`
بالكامل. بما أن قيمة واحدة فقط يمكن أن تُخزَّن في نفس اللحظة، **فتح قسم يُغلق أي قسم آخر تلقائياً
بحكم بنية الحالة نفسها**، لا بمنطق إضافي يُطابق كل الأقسام الأخرى ويغلقها يدوياً — هذا يضمن عدم
انفلات الحالة لاحقاً مهما زاد عدد الأقسام مستقبلاً.

منطق النقر الموحّد (`handleGroupClick`)، يُستدعى من أي مكان في صف القسم (الاسم أو السهم، بلا أي
`stopPropagation` منفصل بعد الآن):
- لو القسم المضغوط هو نفسه الصفحة المعروضة حالياً (`moduleId === id`) → **toggle** بسيط لحالة
  الطي فقط (فتح إن كان مغلقاً، إغلاق إن كان مفتوحاً) بدون أي تنقّل — لأن المستخدم بالفعل واقف
  في هذه الصفحة.
- لو قسم مختلف → `setModuleId(id)` فقط، وينتقل عبرها لصفحة ذلك القسم؛ الفتح التلقائي وإغلاق أي
  قسم آخر مفتوح يحدثان معاً كأثر جانبي طبيعي لتحديث قيمة الحالة الواحدة (بلا أي كود صريح "أغلق
  الباقي").

### فتح تلقائي للقسم الذي يحوي الصفحة الحالية، من أي مصدر تنقّل

الشرط الرابع في الطلب يقتضي أن يبقى القسم الذي فيه الصفحة الحالية مفتوحاً تلقائياً، حتى لو حدث
التنقّل من مكان آخر غير القائمة الجانبية (مثال فعلي وموجود في الكود: زر "لوحة القيادة" الفارغة
"+ إضافة أول شركة من الإعدادات" يستدعي `setModuleId("settings")` مباشرة بلا أي نقر على القائمة).
لتغطية هذا: `useEffect` واحد يراقب `moduleId` ويفتح القسم المطابق تلقائياً كل مرة *يتغيّر* فيها
`moduleId` إلى معرّف قسم فعلي:
```js
useEffect(() => {
  if (NAV_GROUPS.some((g) => g.id === moduleId)) setOpenGroupId(moduleId);
}, [moduleId]);
```
اعتماده على `[moduleId]` (لا فحص عند كل render) مهم جداً هنا: لو أغلق المستخدم يدوياً القائمة
الفرعية للقسم الذي هو فيه بالفعل (نفس الصفحة، Toggle البسيط أعلاه)، لن يُعاد فتحها قسراً في
اللحظة التالية لأن `moduleId` لم يتغيّر فعلياً — هذا يحقق الشرطين الثاني والرابع معاً دون تعارض
بينهما (الإغلاق اليدوي يبقى نافذاً طالما المستخدم لم يغادر الصفحة إلى قسم آخر).

### تصميم بصري

- **انزلاق سلس بدل ظهور/اختفاء مفاجئ**: القائمة الفرعية تُعرَض دائماً في الـ DOM (لا شرط
  `{isOpen && (...)}` كالسابق الذي يمنع أي انتقال CSS)، ويُتحكَّم بارتفاعها عبر
  `grid-template-rows: 0fr ↔ 1fr` على حاوية غلاف (`.nav-subitems-wrap`) مع `overflow: hidden`
  على طبقة داخلية — هذه الحيلة (بدل `max-height` التقليدية) تتحرك بسلاسة دون الحاجة لمعرفة
  الارتفاع الفعلي للمحتوى مسبقاً (عدد العناصر الفرعية يختلف بين الأقسام).
- **دوران السهم بالكامل عبر CSS لا استبدال رمز**: رمز `▾` ثابت واحد يُدار بـ
  `transform: rotate(90deg)` (مغلق، يشير جانباً) إلى `rotate(0deg)` (مفتوح، يشير لأسفل) مع
  `transition: transform`، بدل التبديل بين رمزين نصيين مختلفين (`◂`/`▾`) كما كان — يمنح حركة
  ناعمة بدل قفزة بصرية.
- **أيقونة لكل قسم رئيسي وكل عنصر فرعي**: ملف جديد `legacy/navIcons.jsx` بنفس أسلوب الأيقونات
  الموجودة أصلاً في `legacy/shared.jsx` (خطوط SVG بسيطة 24×24، `currentColor`)، يغطي كل الأقسام
  الثمانية + الشاشة الرئيسية + كل تبويب فرعي داخلها (~45 مفتاحاً). بعض المفاهيم المتطابقة عبر
  أقسام مختلفة (مثل "التقارير" في المبيعات/المشتريات/الأصول الثابتة/شئون الموظفين) تتشارك نفس
  الأيقونة عمداً — التماثل البصري هنا صحيح دلالياً، وليس قصوراً في التنفيذ.
- **تمييز القسم النشط + Hover**: أُبقي على النمط اللوني الموجود أصلاً (حد جانبي ذهبي + خلفية
  فاتحة شفافة لأي عنصر `active`)، وأُضيف تأثير Hover خفيف موحّد لكل من الأزرار الرئيسية والفرعية
  (`rgba(236,230,214,0.05-0.06)`) لم يكن موجوداً على مستوى رأس القسم (`.nav-group-toggle`) سابقاً.

### كيف اختُبرت الميزة فعلياً (متصفح حقيقي عبر Playwright، تسجيل مستأجر جديد فعلياً)

سيناريو واحد غطّى: (1) عدم فتح أي قسم عند التحميل الأول (الصفحة الافتراضية "لوحة القيادة" ليست
قسماً أصلاً)، (2) فتح "المبيعات" بالنقر على اسمه وتأكيد ظهور عناصره الفرعية، (3) فتح "المشتريات"
بعدها مباشرة والتأكد أن "المبيعات" **أُغلق تلقائياً** في نفس اللحظة (لا قسمان مفتوحان معاً)، (4)
النقر على "المشتريات" (المفتوح والنشط بالفعل) مرة أخرى والتأكد من إغلاقه فوراً بينما **يبقى**
معرَّفاً كالقسم النشط (الصفحة لم تتغيّر، فقط القائمة الفرعية طُويت)، (5) تأكيد دوران أيقونة السهم
(فحص وجود/غياب صنف `open` على العنصر) مطابقاً لحالة الفتح/الإغلاق، (6) تأكيد وجود عنصر SVG أيقونة
لكل قسم رئيسي (٨ على الأقل) ولكل عنصر فرعي في قسم المبيعات المفتوح، (7) التأكد أن التنقّل
البرمجي غير المباشر (زر "+ إضافة أول شركة من الإعدادات" في الداشبورد الفارغة، الذي يستدعي
`setModuleId("settings")` مباشرة بلا أي نقر على القائمة الجانبية) يفتح قسم "الإعدادات" تلقائياً
في القائمة الجانبية ويُعلّمه كنشط. **كل الفحوصات الأربعة عشر نجحت.**
