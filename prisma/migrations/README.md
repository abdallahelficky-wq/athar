# قبل كتابة أي migration يدوياً — اقرأ هذا

كل موديل في `schema.prisma` مُعرَّف بـ `@@map` إلى اسم جدول مختلف تماماً (snake_case).
لا يوجد ولا موديل واحد في هذا المخطط اسم جدوله الفعلي مطابق لاسم الموديل في Prisma —
مثال: الموديل `SalesInvoice` جدوله الحقيقي `sales_invoices`، لا `SalesInvoice`.

**أي SQL يُكتَب يدوياً ويشير إلى اسم الموديل بدل اسم الجدول الحقيقي سيفشل عند التطبيق —
100% من الوقت، بلا أي استثناء ممكن في هذا المخطط.**

هذا بالضبط ما حدث فعلياً في `20260915103000_sales_invoice_zatca_retry_tracking`: كُتبت
`ALTER TABLE "SalesInvoice"` بدل `ALTER TABLE "sales_invoices"`. الملف نجح في الجلوس على
القرص بلا أي خطأ ظاهر (لا شيء يُشغِّل SQL وقت الكتابة)، لكنه كان سيفشل حتماً عند أول
`prisma migrate deploy` حقيقي — وبما أن `package.json` يشغِّل
`"start": "prisma migrate deploy && node dist/server.js"`، فشل الـmigration هنا لا يعني
ميزة معطوبة، بل **خادم لا يُقلِع إطلاقاً**، لكل شركة على المنصّة.

## القاعدة

لا تكتب `migration.sql` من الذاكرة أو بالاعتماد على اسم الموديل. دائماً:

1. عدِّل `schema.prisma` بالتغيير المطلوب.
2. شغِّل `npx prisma migrate dev --name <اسم-وصفي>` ضد قاعدة بيانات فعلية تعمل محلياً.
3. دع Prisma يستنتج SQL الفعلي من الفرق الحقيقي بين المخطط وحالة القاعدة الفعلية — هذا
   المسار يفحص أسماء الجداول الحقيقية في القاعدة نفسها، فلا يمكن أن يخطئ فيها كما يخطئ إنسان
   يكتب SQL من الذاكرة.

فحص CI في `.github/workflows/migration-check.yml` يعيد تطبيق كامل تاريخ الـmigrations بنفس
أمر النشر الفعلي (`prisma migrate deploy`) ضد قاعدة بيانات فارغة عند كل push وPR، تحديداً
ليلتقط هذا النوع من الأخطاء قبل وصوله للإنتاج — لكنه خط دفاع أخير، لا بديل عن اتّباع الخطوات
أعلاه من البداية.
